## 今日工作日志

### Provider 服务端开发（实验室）

整个 session 都在构建 Provider——一个后台收敛循环系统，自动扫描所有 scope 的 Tag/CHANGELOG/Release 一致性。

**v0.1.0 → v0.3.0**：从打印一行字的桩，变成了完整的自治系统。

#### 核心进展

- **Artifact 三角扫描**：三路 API（Tag/CHANGELOG/Release），版本号交叉验证
- **状态判定引擎**：13 行判决表覆盖 8 种 artifact 组合状态，区分 `normal` / `missing_changelog` / `missing_release` / `only_tag` / `causal_break` / `pending_release`
- **反脆弱修复**：缺 Release 自动创建、缺 tag 搁置、CL 超前 tag 自动发版
- **后台收敛循环**：可配置间隔的定时器，扫描→判定→修复→重扫全自动
- **Scope 自动发现**：遍历 tag `split_once('/')` 提取 scope 名，扫描 `src/`/`packages/`/`apps/` 匹配目录（对齐 CLI 的 `auto_detect`）
- **CHANGELOG 路径**：通过目录扫描发现，默认 `{scope_name}/CHANGELOG.md`
- **HTTP API**：`GET /health`、`GET /scan`、`GET /scan/:scope`、`GET /report`、`POST /repair/:scope`

## 反思

### 最大的教训：先读 CLI 代码再动手

这个错误今天犯了至少 5 次：

| 轮次 | 被指出问题 | 原因是 |
|------|----------|--------|
| 1 | tags[0] 取了最旧的 tag | 没按 semver 排序 |
| 2 | scope 无前缀过滤 | 没对齐 split_once('/') |
| 3 | CHANGELOG 路径硬编码 | 没对齐 auto_detect |
| 4 | extractFirstVersion 匹配 URL | 正则太宽 |
| 5 | root scope 有废弃 release | 没检查数据 |

每次都是写到一半被用户指出"和 CLI 不一致"才去读代码。先理解、再动手，而不是反过来。

### 其他教训

- **测试写晚了**：核心逻辑（scan、judge、repair）大部分无测试覆盖，bug 只能在真实扫描中暴露
- **真实数据不干净**：repo 总有历史遗留问题，自动化工具必须能处理
- **正则选取要精准**：非结构化文本提取结构化信息，匹配条件越精确越好

## 对用户行为模式的观察

今天的迭代节奏很快——用户对"和 CLI 不一致"非常敏感，每次都是立即指出、不拖。这导致了我频繁回退重写，但最终结果（Provider 和 CLI 的行为对齐）是正确的。

用户倾向于用真实仓库验证，而不是造 mock 数据——Provider 首次跑就扫了 5 个真实 repo 的 11 个 scope，发现了真实的版本不一致和历史遗留问题。这种"直接上生产验证"的风格，让工具在开发阶段就暴露了边界情况。
