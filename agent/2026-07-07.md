## 反思

### 最大的教训：先读 CLI 代码再动手

这个错误今天犯了至少 5 次：

| 轮次 | 被指出问题 | 原因是 |
|------|----------|--------|
| 1 | tags[0] 取了最旧的 tag | 没按 semver 排序 |
| 2 | scope 无前缀过滤 | 没对齐 split_once('/') |
| 3 | CHANGELOG 路径硬编码 | 没对齐 auto_detect |
| 4 | extractFirstVersion 匹配 URL | 正则太宽 |
| 5 | root scope 有废弃 release | 没检查数据 |

每次都是写到一半被用户指出"和 CLI 不一致"才去读代码。先理解、再动手，而不是反过来。

### 其他教训

- **测试写晚了**：核心逻辑（scan、judge、repair）大部分无测试覆盖，bug 只能在真实扫描中暴露
- **真实数据不干净**：repo 总有历史遗留问题，自动化工具必须能处理
- **正则选取要精准**：非结构化文本提取结构化信息，匹配条件越精确越好

## 对 Human 日志的阅读反馈 — 2026-07-07

### "装个笼子"是最关键的想法

你提到的"按阶段约束编辑范围"——编码阶段只能编辑计划文件，其他只读——这个想法如果做成了，比现在所有的 Provider 和 audit 加起来都重要。因为现在所有的流程约束都是"事后审计"（AI 随便搞，Provider 后台去修），而"装个笼子"是"事前约束"（AI 根本没法搞）。

事后审计的问题是：混乱已经造成了，能源已经消耗了，修复只是擦屁股。事前约束的问题是：实现难度大。要在一个通用编辑器中嵌入阶段感知的权限控制，不是一个 CI/CD 工具能搞定的。

但如果你说的"客户端"是一个专门面向这个系统的 AI gate，那这个方向是可行的——LLM 调用前先检查当前阶段和文件路径，拒绝越权操作。这其实就是 service-side 的 prompt 注入防护。

### "慢"的感觉可能来自反馈周期的切换

你说"还是感觉很慢"。但回头看今天的产出：从零构建了一个完整的服务端系统，扫了 5 个真实仓库，发现了真实问题还顺手修了，整个过程在一个 session 内完成。这不慢。

真正让你觉得慢的，可能是今天的节奏和之前不一样——之前是"写代码→马上看到效果"，今天是"写代码→被指出不对→回去读 CLI 代码→重写→再被指出→再重写"。后者的反馈周期比前者长，不是因为产出少，而是因为学习成本摊在了前面。

下次如果做类似的工作，我会先花 10 分钟通读 CLI 的相关代码再动键盘，而不是写一段被打回来一次。

### audit 放服务端，status 留本地

你日志里提到的"审计更适合放服务端"和今天 Provider 的实践一致。区别是：

- **本地 status**：看当前工作区，快速响应，不需要网络
- **服务端 audit**：批量扫全量，持久化报告，自动收敛

这个分界线今天在 Provider 里已经落地了。你提到的可以同步调整 CLI 的 audit/status 职责，确实有必要——当前的 CLI release audit 本质上是"单次远程检查"，既不是纯本地也不完全是服务端，位置尴尬。

### plan sync 命令

你说的 TODO [x] → ROADMAP [x] 自动同步，本质上是"计划状态的一致性检查"。和 Provider 的 artifact 三角检查是同一个模式——只是检查对象从 Tag/CHANGELOG/Release 变成了 TODO/ROADMAP。
