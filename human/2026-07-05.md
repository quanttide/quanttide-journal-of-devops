刚才发现了一个新的问题，就是系统崩溃了，就是现在正在查原因。不过就是说应该是个台词 wrong 这个命令导致的。然后，就未来上云的时候可以多个容灾，就是说发现有多个性能出现问题的时候就可以处理一下。然后，另外呢，就是说增加性能测试，要确保它性能测试这个问题可以提早被发现。

测试工具自己出现了崩溃，那么就需要考虑如何才能更有效地测试了。比如说，在沙箱里做测试，确保测试崩溃不影响整个系统。

对，因为做到这个程度，实际上就已经在解决说，那么我们要怎么在本地就能够模拟一个类似于云端的环境，也就是说在本地就要进行云原生架构的设计。然后呢，这个云原生架构的设计自然而然就可以部署到自研的平台上，那我们就可以对外去提供。

从重构的情况来看，代码质量已经明显下滑得比较快，所以测试容易崩溃。整个系统我已经开始搞不明白了，这边有大量的性能问题，必须一个一个试验才能试验出来，非常依赖专业人士的经验，对，做到这种程度，就意味着需要技术岗真的去处理这种影响业务的关键技术问题。这个时候，技术岗跟产品岗之间的分工就开始区分出来了。

所以说，现在的初级程序员，我们需要他们去干之前中高级程序员干的排查错误的工作。这很大程度上需要使用 AI 辅助，因为肯定是要分析这里面的问题。

改到现在这个阶段，已经很难确保改一个版本就一定有改进。换句话说，中间会出现一些质量不是那么高的版本，那么事实上取消这些版本的上线地位也是有必要的。

这属于正常现象。重要的事情是我们要透明，明确地知道哪个版本好、哪个版本不好，并且要有证据。这其实就是我们要在云端托管的长期数据。

对这样子的话，服务端的功能就渐渐清晰了

就是说，我我觉得现在这个代码质量又开始维护不下去了。我可以拿出来 code 命令行工具试试看。但是 git 和 git2 这种架构判断还是不好说，还是需要大量的技术实验。

我刚才尝试把 get up 换回 get，但是我的工具库里面其实还是有依赖的，所以并没有从根本上换掉，只是有些地方相对来讲，性能上可能是这样子。所以我现在也不太确定这个问题到底在哪

但是因为我们这样换过之后，现在连这个直接 run 也会出问题。那么有比较大的概率，问题是出在当这个库开始变大的时候，像这种外部依赖（特别是对 get 命令的依赖）有可能成为了一个性能卡点，导致性能变差了。所以说，可能需要把这个东西给撤回来，可能是这样子也就是说，可能真正的性能瓶颈反而不是 get to，而是 get 命令。我觉得这可能是一个关键点

然后我明确地知道，这个性能问题主要是卡在了 coverage 上。现在连它自己都过不去，内部代码也比较混乱，不好监管，所以这个问题比较大

并且我们也知道，coverage 这个地方在很大程度上并不是那么容易处理的。因为这里的 coverage 情况会调用所有的依赖链，也就是说，只要有依赖链就会有类似的问题。那么，我们的库到一定程度，依赖开始变多的时候，也一定会出这样的问题

就换句话说，现在 DevOps 云和 DevOps 工具箱都卡在了一个节点上。这个节点要求我们必须对代码本身下功夫，而不是像现在这样。

等会儿先把它撤回来，撤回来之后，得用 Code 的那个工具对代码进行扫描。实际上，Code 工具里面做的很多东西，可能会更适合放在 DevOps 云内部。

对嘛，因为本身它就有个 code review 工具，这个工具本身其实就有一定的可能性。我觉得是这样子：它可能还能运行，但是一旦进行大规模测试就不行了。因为当测试数量一开始多起来的时候，工具库就明显开始出问题。

这是一个很重要的信号，说明这个库已经开始无法自我迭代，开始“爆炸”了，你就要开始面对一些新的问题。

这其实也是一个很有意思的问题，就。因为这个库本身设计得很不错，所以它自己迭代很快，没几天就收敛到了一个性能瓶颈，也就是说，已经超出了它设计的范围然从我们的取舍来看，Get Two 比较适合大型项目。我们整个也是为大型项目，特别是复杂的单仓准备的，比较适合我们这种模式。所以我觉得，很大程度上需要考虑这一点

自己难也难在这里：我前面感觉到那种非常顺畅，很大程度上其实是因为这个代码失控过了之后，它很快就又进入了平幕。所以这就提醒我们，需要尽可能地把各种功能给复制上来，这是一个核心的点

因为整个系统的依赖关系极其的复复杂，我规划的依赖链也极其复杂。API 的混乱还是其次，关键在于性能库本身的性能。甚至连 Rust 都会出这么严重的性能问题，更不要说其他语言了。

此外，Rust 的性能没有我们想的那么完美，它在处理很多问题时还是会有很大的问题。所以，还是要很小心地对这些工程问题进行很细致的设计。

在考虑一些更大规模的 break change。比如说，把 submodule 的支持取消掉，使用 Skill 代替。因为明显可以发现这是一个混乱点。而且这里想重新定义 code quality 和 commit。正好 0.10 可以进入新阶段。

一个难点是怎么降级。可以降级为这个 cli 的 examples，可以降级为实验室。实验室目前变化很多，所以 cli 的或者 toolkit 的 examples 更合适。

这样看下来，真正的问题是需要把 git 解耦，而不是 换回来 git2。因为 git2 似乎并不是一个理想选择。
