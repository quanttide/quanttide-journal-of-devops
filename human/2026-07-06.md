我尝试对库的逻辑进行了重新整理和加工。目前 0.2 版本已经成功地把事实源和契约做了一个基本的分层。但是我不确定，假设用它来生成工程标准，不知道质量怎么样，会不会质量很低下。我想再稳定一点再开始写工程标准。而且也不要求工程标准跟工具库之间有强制同步关系，所以我觉得可以先等一等。

目前版本已发到了 0.2.2。0.2.3 版本打算更新一些 change log 的功能，主要是发现了一些小问题，准备更新一下。

关于 LLM，先不在这个库里面引入，只要能让它模拟执行流程就可以了。这样有一个好处，就是可以让各个领域库之间不相互依赖。

如果实在发现 LLM 这个类用得太广泛，我们再把它写到底层的库里面就可以了。因为规定只有一个最底层的库可以作为其他东西的底层，这个规定就是为了防止这种情况出现。

另外还有一些新的发现。比如 MYST 这个文档框架，我也想把它加进流程里面，让它作为一个文档框架去识别。我觉得可以去拓展一下。

或者还有一种做法，就是我可以把仓库的默认语言设成 Markdown，然后把 MyST 作为一种 Markdown 的方言去识别，类似于像 uv 一样去识别，这也是完全可以的。

它不像编程语言那么严格，所以去做可能会把流程搞乱掉。但是如果能做出来的话，有个明显的好处，就是我们可以把所有的文档仓库都纳入到统一的流程里面。

这个可以明天再看一看。它可能不能直接上，要先往实验室里试一下看看效果，然后再决定。

现在把各种逻辑都写到库里面之后，会有一个明显的缺点：如果上层需要增加或删减一些东西，就不像之前那么敏捷了。比如，假设要增加或减少一种语言，就得去更新工具库然后再引入，这样有时候就显得不够敏捷。

但是好处是，相对来讲更稳一点，可以进行更严格的测试。当然，在上层直接复制并重写也是可以的，但这样一来，工作量反而会更大一点。

目前我以第二大脑作为中心，做了大概 5 个标准的对话框。同时，我正在进行平台库和实验室的工作实验室被我放在了第二大脑顶层，因为它可能需要从整个第二大脑调取信息并进行处理。

云和平台都需要保持一定的独立性，所以我单独为它们开了窗口，每个窗口各设两个对话：
1. 一个对话是 Open Code，负责根据写好的 To-do 去执行。
2. 另外一个是上个。那另外一个是一个 z agent 的那个窗口，然后我们需要他评评审对。

因为很多发布工具一类的，我们都统一放在了“第二大脑”功能里，所以一些流程性的工作还是得在上层去走。这是目前一个刻意的设计。

这个设计的主要目的是，虽然放在系统和目录里面可以解决这个问题，但是放进去不透明，不好维护，暂时不想这样搞。 

考虑将 plan doctor 命令改成一个编辑命令，比如叫 edit 或者叫“整理”一类的命令。它的基本设计是：假设我的 roadmap 是混乱的，我需要把它整理成一个比较规范的格式。你像 clean，它也可以被改成一个支持 LM 的模式。就是说，我可以做两层工作，一层工作是在对市场判上，一层工作是在语义上。

这样子的话，在我们的整个架构系平能案这个能力只专注于 roadmap 和 todo，其他的都不管。

我再考虑把审计命令我在考虑把审计命令从各种命令和 status 里面拆出来，因为我发现如果呃都混在里边的话，整个逻辑就非常的臃肿，然后呢，就不太好做

对，就是我们应该要做的事情，是想办法去封装一个提示词或者是 skill，让它在二级命令上更加灵活和自由一点，而不是把所有的三级命令都压成一个大命令。

这样的话非常不灵活、没弹性，每一个命令都非常臃肿，带着一大堆状态。比如 publish 这个命令就会出现这种问题，导致发布这个过程本身不纯粹，变得非常复杂。

因为 DevOps 这种场景规则多、目标明确，所以它其实是一个很好的用来做审计驱动验证的做法。它有大量的规则可以用来审计，我觉得这也是一个很重要的点

然后我打算把像 test 的审计、code 的审计这些，都拿到整个设计里面。这样一来，我们全流程的每个阶段都先审计起来，再做一个总的审计。

就像 status 一样，有一个静态的状态，有一个动态的审计。这样 status 就不需要去承担 audit 的职责了，分工就比较清楚。然后因为经过这样的分解，一定会出现需要存储状态的现象，因此我们需要开始考虑本地缓存的需求，一定要考虑怎么才能把这些东西存下来。

同时，服务端也要开始考虑了。因为一旦本地有了缓存，就意味着服务端的需求也会逐渐提上日程。

对，就从从这些设计来看，有很多组件已经不可避免地需要提上来了。如果只有纯命令行，它只能降级，没有状态缓存，非常浪费效率。所以，像本地缓存或者云端存储，就要开始提上日程了

对这这种设计非常惊艳，很具备价值。我觉得这种构建思路应该是对的，能明显感觉到这个系统开始在快速迭代像 test run 这些只是简单 wiper 的，其实没有什么大用。把这种命令干掉完全可行，并不影响整个系统的运行
就反反而是各种审计工具要加强，像 review 的话，我还没考虑好要不要加。

因为从目前的流程来看，感觉像 review、refactor 这些装进去也行，但是会让整个流程变得非常混乱，定位不够干净。其实维持我们之前这种专门的 code 命令去进行 review 和 refactor，可能会更好一点。如果要按这个逻辑来设计的话，可能 test 也需要一个专门的命令，专门用来解决 AI 写 test 不够到位的问题。这样的话，命令行可能就会比较碎一点


如果以审计功能作为骨干，其他命令（比如 publish 命令）只是一些自动化操作，并且里面的 Agent 只是专门用来处理其中的一些细节问题，那么这个工具就会比较精干。

因为它本身有很多次命令，加起来又比较复杂，所以把 review 命令全面地从它里面干掉，其实是比较合适的。

今天新发现了一个问题：如果我们需要频繁地将自研库发布到 Rust 的制品库中，就不太适合使用国内的镜像源。

因为在配置上，它只允许设置一个镜像源，且不允许替换。这是为了防止构建依赖出问题，但这也是一个很大的限制，因为我们实际上还是需要这个功能的。如果需要修改，就只能去改配置文件，这是一个比较大的问题点。

这个在云端上比较好解决，因为在云端的构建环境上，我们可以每次生成一个系统环境，每次都可以切换。但在本地的话，这个就很难改了。

这个的做法是：如果你是用户，你可以去换；如果你是维护者，特别是像我这种高权限的维护者，那么其实官网反而会更好一点。

这是由它的语言机制决定的，这个语言要怎么换，就不像 Python 一样那么灵活。
