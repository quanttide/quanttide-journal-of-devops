真的是他山之玉可以攻石。一开始，我只是想要解决自己的认知问题，做着做着，把它从文档迁移到了代码，做出了一个更高质量的代码审计工具，可以自己审自己的。

后来，我发现旧的 DevOps 里面的代码审计功能非常糟糕，就顺手把它重构掉了。并且我意识到，这个代码审计工具在很大程度上可以帮助我们去认知现在所有的代码资源。那么，这一下子它的价值就开始突飞猛进了。

通过限制圈复杂度、函数长度等方式，可以很大程度管住代码的下限。

对，等一下让他加强一下模块级的治理，对一些代码里的细节慢慢去扒拉就可以了。刚才我把整个模块变成了以 stage 为中心的 2 级、3 级命令，这样一下子就清楚了。严格根据 command 暴露的命令进行分析，这样的一大好处就是我们可以去处理实际的情况。把各种需要分装的数据模型都一对一地对上，这样就好重构了。

嗯，我知道了，我缺了一个关键的方法论，就是这么对齐过之后，它其实具备了这种从平台到库的这种分装，再下一步就是要再下一步就是需要一个自动化的判断流程啊，不是靠人为一个判断这个一旦搭起来，那么我们的这个标准化就会空前地加快了。

就我我觉得这样放松下来，重新思考过之后，获得了一个非常关键的点：感觉到不对的时候，一定要停下来想一想怎么才能够更有效率，并且我一定觉得它是可行的。下来，想一想，怎么才能够更有效率，并且我仅是觉得他是可行的。

对，我觉得我获得了一种系统的方法，让代码的混乱和我的维护责任分离开，并且我能够在这个基础上进一步找到我想要的点。

而且，有一个关键的功能划分变化：重构这个环节很大程度上应该放在 DevOps 体系之中，不需要放在代码的命令里面。这样的话，整个研发自动化流程也会变得更加完整。

在这个体系之下，我们假设目标已经比较清晰，不太需要通过探索式的编程来寻找方向。我的意图是清晰的，代码也是有的。大比例的工作是足够的，小比例可能顺手增加一些新功能，这些都可以在人类的监督下去完成。这其实就是我们要达到的 DevOps 目标。

关键点就是，如果我对中间的交付质量没有要求，只关注能不能完成单个任务，那么我的认知负担是比较轻的。但是，一旦让我让这个代码可控，认知负担就会急剧增加。这其实也就是 DevOps 体系的作用。

这个关键的技巧是：通过个别的问题去找到一类模式，把这类模式翻译成一个架构师的经验，然后让 AI 用这个经验去查。

工具、手册这些东西的本质，其实就是把架构师的经验固定下来。

爱的建议是，在写平台的同时就开始抽取库，把数据结构等都给抽出来。

我觉得这个想法挺好的，两个同步进行，确实是避免技术债务扩大的一个很重要的办法。因为如果要修改的话，数据结构单独用库修改也比较容易，修改完之后再强制集成就可以。

而且我好像发现了一种新的“左脚踩右脚”的结构：上层平台不断往下层堆数据模型，当下层数据模型乱到一定程度后，上层平台能稍微好用一点，再来去改进下层的平台，然后不断循环。这样也是一个可以让 DevOps 语音快速迭代的方法。不过我不太确定这个字句对于其他的领域有没有帮助，或者有没有类似的效应。

这个发布命令的定义其实稍微有点问题。如果把它定义成：
1. 先 prepare，处理本地仓库；
2. 然后执行或发布，把 get tag、get release 创建上；
3. 如果需要的话，也可以直接去发包。我们现在的逻辑是用 CI 处罚。CI 处罚有一个职业的缺点，就是比较费事；但它有个好处，相对来讲比较稳定，可以进行稳定的检查。

从概念定义上来讲，这个地方其实还不是很严谨。因为直接的结果就是 CI 不不是很透明，它并没有被包含在发布过程之中，也就是上传到制品库最关键的一个过程没有被包括进去。

会存在云端和本地混合，但是云端的数据没有同步到本地，这种非常怪异的现象。 

这有一个直接的后果：比如命令行工具本身 build 失败是一个很常见的问题。失败后它会终止 CI，但是本地的 build 命令比较弱，发现不了问题。
